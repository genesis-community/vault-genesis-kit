# Vault Genesis Kit Manual

The **Vault Genesis Kit** deploys a consul-backed Vault cluster.
Vault provides secure storage of and access to sensitive
credentials used elsewhere in deployments and applications.

## Version Compatibility

This kit requires Genesis 3.1.0 or higher. It is currently at version 3.0.0.

## Features

The following features are supported by this kit:

- `ocfp` - Uses the config generated by the OCFP scripts that initialize the
  infrastructure, and sets opinionated configurations.  This has the following
  effects:

  * sets the network, vm_type and disk_type to unique name specific to this
    environment, so no chance of conflict or inadvertent changes.

  * provides the ips and azs that will be used by the network.  Setting
    `params.ocfp-instances` will allow a subset of these ips.

  * Provide a generated cloud config to specify the above values that will be
    uploaded prior to deployment.

- `stackit` - Configures the deployment for the STACKIT cloud platform. This
  sets up the appropriate VM extensions and other STACKIT-specific settings.

- `azure` - Configures the deployment for Microsoft Azure, including setting
  up availability sets for the Vault nodes.

- `resolute` - Deploys the Vault nodes on the Ubuntu resolute (26.04) stemcell.
  See [Ubuntu Resolute Stemcells](#ubuntu-resolute-stemcells).

## Base Parameters

- `vault_disk_type` - The persistent disk type that the Vault VMs will use.
  This replaces `vault_disk_pool`, which will still work if vault_disk_type
  is not specified.  This vm type must exist in your cloud config.  Defaults
  to `default`

- `vault_vm_type` - What type of VM to deploy.  This type must
  exist in your cloud config.  Defaults to `default`.

- `vault_network` - What network to deploy Vault into.  This
  network must be defined in your cloud config.  Defaults to
  `vault`.

- `vault_domain` - Domain for vault certs to be signed for. Defaults to `vault.bosh`

- `ips` - If you want to have full control over the number of instances to
  deploy to, just specify the IPs of those instances in a list and those will
  be what is deployed.  Specify one IP, one vm will be used; specify 5, 5 vms
  will be created.

  NOTE:  Fault tolerance of Vault is N/2+1 remaining instances, so even-counts
  of VMs don't increase fault tolerance over one less than that count.  For
  this reason, it is recommended that odd-counts of IPs are specified.  See
  https://www.consul.io/docs/architecture/consensus#deployment-table for full
  details.

- `availability_zones` - What BOSH HA availability zones to deploy
  the Vault across.  The chosen network must have at least one
  subnet in each of the listed zones, and the zones themselves
  must be defined in your cloud config.  Defaults to `z1`, `z2`,
  and `z3`.

- `stemcell_os` - The operating system stemcell you want to deploy
  on. (default: `ubuntu-jammy`, or `ubuntu-resolute` when the `resolute` feature is on)

- `stemcell_version` - The specific version of the stemcell you want
  to deploy on. (default: `latest`)

- `azure_availability_set` - In Microsoft Azure, this parameter
  names the availability set to deploy the Vault nodes across.
  This parameter does not have any effect on other platforms.

- `auxiliary_vault` - If deploying a second Vault after the
  primary Genesis Vault was deployed. This prevents automatic
  unsealing of the Vault after a deploy, as Genesis will attempt
  to unseal the new Vault with the seal keys of the primary
  Genesis Vault. Defaults to `false`.

- `ui` - If true, the Vault Web UI will be turned on. Defaults to true.

## OCFP-specific Parameters

- `ocfp-subnet-prefix` - specifies the subnet prefix for subnets that will be used
  to populate the network components on this environment.  Defaults to `ocfp`

- `ocfp-instances` - specify how many instances to use out of the total provided
  by the OCFP configuration.

## STACKIT-specific Parameters

- STACKIT cloud provider settings follow the general parameters structure.
  Any STACKIT-specific VM extensions can be configured in the deployment manifest.

## Cloud Configuration

By default, Vault uses the following VM types/networks/disk pools from your
cloud config. Feel free to override them in your environment, if you would
rather they use entities already existing in your cloud config:

```
params:
  vault_network:   vault
  vault_disk_pool: default # should be at least 1GB
  vault_vm_type:   default # VMs should have at least 1 CPU, and 1GB of memory
```

## Available Addons

- `init` - Initializes the Vault cluster.  This can only be run once, as it
  formats the Vault storage and generates seal keys for protecting the Vault.

- `target` - Sets up a `safe` target for this Vault, named after the
  environment, and prompts for authentication.  Takes an optional
  `<auth-type>` argument to specify the auth method, such as `github` or
  `userpass`, defaulting to `token` if not provided.

- `status` - Determine Vault status: health, availability, and sealed /
  unsealed state.

- `seal` - Seals the Vault.

- `unseal` - Unseals the Vault.

## Examples

To use custom cloud config types:

```
---
kit:
  name: vault
  version: 3.0.0

genesis:
  env: acme-us-east-1-prod

params:
  vault_network:   credstore
  vault_disk_pool: encrypted
  vault_vm_type:   std.small.1c.2gb
```

To deploy on STACKIT:

```
---
kit:
  name: vault
  version: 3.0.0

genesis:
  env: stackit-eu-prod

features:
  - stackit

params:
  vault_network: vault-network
  vault_vm_type: medium
  vault_disk_type: large
```

To deploy using OCFP configurations:

```
---
kit:
  name: vault
  version: 3.0.0

genesis:
  env: ocfp-us-prod

features:
  - ocfp

params:
  ocfp-instances: 3
```

## Ubuntu Resolute Stemcells

The `resolute` feature deploys the Vault nodes on the `ubuntu-resolute` stemcell, which is Ubuntu 26.04. The feature sets `params.stemcell_os` to `ubuntu-resolute` for you, so leave that parameter out of the environment file. The kit refuses to build the manifest when the feature is on and `params.stemcell_os` names a different operating system. It also refuses to build when `params.stemcell_os` is `ubuntu-resolute` and the feature is off, so the feature is the one place where the choice is made.

Set `params.stemcell_version` to a resolute stemcell your Director holds. The kit was tested with `0.184`. The Director also needs bosh-dns 1.39.31 or later, because earlier bosh-dns releases do not start on resolute.

```
---
kit:
  name: vault
  version: 3.0.0
  features:
    - resolute

genesis:
  env: acme-us-east-1-prod

params:
  stemcell_version: "0.184"
```

The resolute stemcell does not ship runit, so the safe release starts its processes with `setpriv` from util-linux in place of `chpst`. The kit pins a safe release that does this on every stemcell, not only on resolute.

The safe release that the kit pins is a development build with the version `0.3.2+dev.1` and no download URL. The Director must already hold that release before you deploy, so upload the tarball with `bosh upload-release` first. The kit switches to a final release with a URL and checksum once one is published.

## Vault and Consul Licence Change

This kit now deploys Vault 2.2.0 and Consul 2.0.4. Both are published by HashiCorp under the Business Source License 1.1, which replaced the Mozilla Public License that covered the Vault 1.14 and Consul 1.16 releases this kit used before. The BUSL allows production use, including running Vault for your own organisation, but it restricts offering the software as a competing hosted service. Read the licence before you adopt the kit if you resell or host Vault for others.

## Upgrading from Kit 2.x

Work through these steps in order when you move an existing environment from kit 2.x.

1. Take a Consul snapshot and keep the Vault unseal keys and root token somewhere outside the Vault. A Vault that a 2.x server has unsealed cannot be rolled back to 1.14, so the snapshot is your only way back.

2. Plan the Consul jump. Consul supports upgrading across at most two major versions in one step, and going from 1.16 to 2.0 is further than that. Either deploy through the intermediate kit versions that carry Consul 1.18, 1.20, and 1.22 in turn, or build a new environment on this kit and restore the Consul snapshot into it.

3. Set `kit.version` to 3.0.0 in each environment file and upgrade Genesis to 3.1.0 or later.

4. Deploy one environment at a time. BOSH replaces the nodes one by one, and the Vault will seal itself as it does after every deploy, so unseal it with `genesis <env> do unseal` when the deploy ends.

5. Expect the existing servers to keep their BoltDB raft log. Consul writes new clusters with the WAL log store, but a server that already has a `raft.db` file keeps using BoltDB and is not migrated automatically. That is safe, and a rebuilt node picks up WAL.

The kit now renders the `storage "consul"` stanza in place of the older `backend` stanza, takes the Consul TLS settings from `tls.defaults`, and no longer sets `start_join`, so the configuration files carry no deprecation warnings. You do not need to change any environment parameters for these.

Vault 2.x also tightens a few behaviours that matter to the clients of your Vault. It rejects request paths that are not cleaned, it limits RSA keys to a modulus of 8192 bits, and it requires a token to rekey or generate a root token. Check scripts that call the Vault API directly before you upgrade.

## Caveats

Each Vault installation will have its own seal keys and initial
root token.  The natural inclination will be to store these _in_
the Vault, but that's a bad idea.  Use an external password
manager instead, like 1password or LastPass.

Every time Vault is deployed, whether to pick up configuration
changes or to upgrade the operating system (stemcell), the Vault
will protectively seal itself.  An operator **must** intervene to
unseal it, or it will remain inaccessible.

## History

Version 3.0.0 adds the `resolute` feature for the Ubuntu 26.04 stemcell, moves to Vault 2.2.0 and Consul 2.0.4, and pins a safe release that starts its processes with `setpriv` in place of `chpst`.

Version 2.0.0 adds support for additional cloud providers (STACKIT, OCFP) and
updates to the newer stemcell versions.

Version 1.2.0 was the first version to support Genesis 2.6 hooks
for addon scripts and `genesis info`.

Up through version 1.1.0 of this kit, there was a subkit / feature
called `shield` which colocated the SHIELD agent for performing
local backups of the consul cluster.  As of version 1.2.0, this
model is no longer supported; operators are encouraged to use BOSH
runtime configs to colocate addon jobs instead.
